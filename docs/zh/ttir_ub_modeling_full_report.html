Triton-Ascend · UB Early Pruning

TTIR UB 保守建模
行业方法、LLVM TTI 与全量落地方案

目标不是预测完整 UB peak，而是在 canonical TTIR 阶段构造一条可审计的下界证据链：只有证据链得到的 UB 下界严格超过目标芯片容量，才提前淘汰 autotune config。

一句话方案：每个 config 生成一份完整 TTIR；用 matcher 提取“必然 UB 物化”的资源；用与真实 pipeline 绑定的 UBResourceContract 逐阶段传递资源下界；最终生成 certificate，并与硬件容量比较。

模型定位

以抽象解释/语义事实传播为主，辅以解析公式；不是统计回归，也不是完整后端模拟器。

核心资产

MURG 保存资源下界事实；UBResourceContract 负责逐 lowering stage 更新这些事实。

当前事实

P0 可执行合同链已接通；direct-copy、binary-add、reshape-copy、reduction-sum 与 loop-carried-add 五类切片，以及 loop-carried-add 的固定双缓冲子切片，均已在目标 CANN 环境完成 analyzer + 独立 semantic replay + 真实 PlanMemory 的 20 seeds/retry 零违规验证，并生成待人工审核 candidate。packaged profile 仍为空，因此真实运行继续安全 defer。

1. 编译器领域的三类建模

“建模”不是特指机器学习。一个模型通常包含四部分：现实对象、关注的可观测量、被省略的状态、从输入推导目标性质的规则。编译器领域常见三类方法：

Analytical / Formula Model

做法：根据 workload shape、循环、mapping 和硬件参数，用闭式公式或组合算法计算 working set、访存、性能或能耗。

典型：Timeloop 对 tensor algebra mapping 和分层存储 working set 做快速解析建模。

优势：快、可解释、适合大规模设计空间搜索。

限制：公式适用条件必须明确；复杂 compiler rewrite 容易使公式失真。

Cost Model

做法：对候选 IR 操作或 transformation 返回 target-aware cost，供 vectorization、unrolling、inlining 等优化比较方案。

典型：LLVM TargetTransformInfo。

优势：接口稳定、查询粒度细、易嵌入优化决策。

限制：通常是相对代价或估计，不是资源安全证明。

Semantic Model / Simulator

做法：在简化状态空间中执行语义或事件规则，传播状态并观察最终性质。

典型：抽象解释、数据流分析；更详细的一端是 gem5 的事件驱动系统模拟。

优势：能表达 alias、liveness、control flow 和阶段性状态变化。

限制：状态越细，复杂度和维护成本越高。

我们的定位：不是 TTI 式“某个 op 大概多贵”，也不是 gem5/PlanMemory 的完整重放；而是一个保守的 abstract resource interpretation：MURG 是抽象状态，contracts 是 transfer functions，公式只用于 shape bytes、tile 下界和资源求和。

2. LLVM TargetTransformInfo 是什么

TargetTransformInfo（TTI）是 LLVM 中连接“目标无关 IR 优化”与“目标相关 codegen 信息”的查询接口。IR pass 不需要执行完整机器码生成，就可以询问目标后端：

Cost queries

  • getInstructionCost
  • getArithmeticInstrCost
  • getMemoryOpCost
  • getCastInstrCost
  • getCmpSelInstrCost
  • getIntrinsicInstrCost

Legality / preference queries

  • vector width、register width、legalization cost
  • unrolling / peeling preferences
  • masked/interleaved memory access legality
  • address-space alias capability
  • hardware-loop、reduction、intrinsic 能力

Cost 通过 InstructionCost 返回，并区分 reciprocal throughput、latency、code size、size-and-latency 等 TargetCostKind。这些值用于比较 transformation 是否值得做，不是“最终机器程序一定耗费多少周期”的证明。

IR optimizationLoopVectorize / SLP / Unroll 等准备多个候选
→
TTI query询问每个候选在当前 target/subtarget 的代价与合法性
→
Decision比较 scalar/vector、不同 VF 或 transformation 方案
关键区别：TTI 的主要任务是“优化收益决策”；我们的 UB 模型的任务是“形成可用于 hard rejection 的安全下界”。前者允许近似，后者不能高估。

3. LLVM TTI 如何实现

Consumer
目标无关优化 pass 从 FunctionAnalysisManager 获取 TargetIRAnalysis 的结果，并调用统一的 TargetTransformInfo API。
Facade / type erasure
TargetTransformInfo 持有实现对象，通过统一接口转发查询；调用方不依赖 X86/AArch64 等具体类型。
Generic fallback
TargetTransformInfoImplBase、TargetTransformInfoImplCRTPBase<T> 与 BasicTTIImplBase<T> 提供 DataLayout、type legalization 和通用默认实现。
Target implementation
AArch64TTIImpl、X86TTIImpl 等只覆盖需要更精确 target knowledge 的 hooks，其余回退到 base。
Target knowledge
Subtarget features、TargetLowering、legal type/action、scheduler model、指令 cost tables、ISA 特殊模式。

典型调用链

Optimization Pass → FAM.getResult<TargetIRAnalysis>(Function) → TargetTransformInfo::get*Cost(...) → target-specific TTIImpl override → generic BasicTTI fallback when not overridden → InstructionCost / legality / preference

值得借鉴的工程模式

Stable query facade

优化 pass 面向稳定接口，不直接依赖具体 target 实现。

Generic + target overrides

通用规则集中复用，目标后端只覆盖差异。

Invalid / unknown handling

无法可靠定价时返回 invalid 或保守默认，调用方决定回退。

对我们的启发：可以把 UB 分析也设计为稳定 query facade + generic MURG solver + pipeline/target-specific contract implementation；但必须保留“未知即 defer”，不能照搬 cost model 的近似策略。

6. PipelineIdentity 与 profile 的真实作用

PipelineIdentity 不保存 TTIR 文本，也不计算 UB；它保存完整 canonical TTIR 文本的 SHA256，并作为“输入 + 合同适用环境”的指纹。当前代码还从与真实编译相同的 PassManager builder 调用 get_pipeline_str()，加入影响 UB 的选项、target、Triton/CANN 版本、实际 NPU compiler 类型与文件内容 SHA256。文件型 BiSheng 参数不记录机器相关的绝对路径：例如 -cce-link-aicore-ll-module 会规范化为文件内容 SHA256，保证同内容换安装目录仍命中、内容改变必定失配。

Validated pipeline P1固定 pass 顺序、参数、target 和 compiler 版本
→
Profile P1记录每个 stage 应使用的 contract id/version
→
Current compile重新计算 identity；完全相等才允许装载 P1 contracts

Identity 命中

当前 pipeline 与验证环境一致，按 profile 顺序应用 contracts。

Identity 不命中

可能有 pass/参数/版本漂移，旧 contracts 禁止复用，立即 defer。

P0 已接通：共享 PassManager builder 在添加 pass 时同步记录有序 pipeline_stages 及类型保持的 options；binding 可按完整 identity、stage ordinal、options、contract id/version 把 profile 装载成只读 registry。packaged profiles 仍为空，因此尚不会启用真实 reject。

7. Matcher 与 MURG：如何从完整 TTIR 得到资源

matcher 遍历完整 ModuleOp，并沿 SSA use-def graph 匹配语义子图；不是按文本行切割，也不是每个 operation 都生成资源。

“证明”不是定理证明器。这里更准确的说法是可审计的下界证据链：matcher 先提出一个带前置条件的资源事实，后续每个 stage 要么确认该事实仍成立，要么把它保守地改小，要么宣布无法继续保证并 Invalidate。只有证据链没有断，solver 才能使用这个资源。MURG 因而也可以直观地叫作“资源下界证据图”。最终 certificate 会携带 contract_trace，逐项记录 matcher 与各 stage 实际采用的 contract id；debug JSON 可以直接回答“这个下界经过了哪些规则”。

当前 V1 pattern

make_range(0, N) + splat(GM pointer) + addptr + unmasked tt.load → single-use unmasked tt.store

要求单 public function、单 block、静态一维 shape、连续 GM pointer、无额外 use、无未知 op。

生成的资源

R0.kind = GMToUBLoad R0.minPayloadBytes = N × element_bytes R0.minInstances = 1 R0.trace = ["ttir-direct-load-v1"]

它只是 source candidate；只有后续 materialization 和所有 stage contracts 都保留证明，才能进入 solver。

优先级原则

  1. 先覆盖 autotune 高频且 UB overflow 收益最大的 pattern，不追求一次性接受所有 TTIR。
  2. 每扩一个 operation family，必须同时补 source matcher、MURG resource/relations、全 stage contracts 和 PlanMemory oracle fixture。
  3. 只扩大 matcher、不补合同，是禁止的；它会把 TTIR logical tensor 错当成最终 physical buffer。

9. UBResourceContract 全量清单

Contract 是一个 stage 的资源事实更新规则：输入是 stage 之前的 MURG，输出是该 stage 之后仍然成立的最小资源事实；不能保证时必须返回 Invalidate。数据流分析里把这种“状态经过一步后如何变化”的函数称为 transfer function。

真实 pass 与 Contract 的关系

真实 pass: Fstage(IRbefore) → IRafter 资源摘要: Tstage(MURGbefore) → MURGafter | Invalidate

Tstage 不需要生成 IRafter；但它输出的每一条资源事实，都必须对真实 Fstage 的结果成立。

一条证据链示例

TTIR: N 个 fp16 必须被读取 → materialize: 必须出现一个 UB buffer → 最多切成 4 块: 至少一块 ≥ ceil(2N/4) bytes → 后续 Preserve → ActualUBPeak ≥ 该块大小

任一步只能说“可能如此”而不能说“必然如此”，证据链就在该步终止，最终结果 defer。

9.1 ResourceContract 到底如何实现

它不是纯公式表，也不应该重新实现一套完整 pass 模拟器。生产实现应允许四类合同；具体 stage 选最小且足够可靠的一类：

合同实现类型做什么例子
PreserveContract在严格前置条件下，确认资源大小、实例数和关系都不变只增加 annotation，且验证不会改变 UB materialization
FormulaContract用 pass 的确定性参数更新数值下界最多切成 K 个 tile，则最大 tile 至少为 ceil(B/K)
SemanticRelationContract按 pass 语义更新资源身份和关系，而不重建完整 IRview 建立 mustAlias；multibuffer 更新 minInstances；code motion 更新 lifetime/witness
ReplayBackedContract在输入边界兼容且开销可接受时，复用已有语义重放，再把结果投影成 MURG 事实复用 CV/Bufferization/PlanMemory 前后的 allocation、alias、liveness 结果
InvalidateContract前置条件、版本或语义覆盖不足时终止该资源证据链未知 op、动态 shape、未覆盖的 SplitMix 分支

9.2 与现有 cvpipeline_ub_model_cpp 的区别

维度现有语义重放模型本方案 ResourceContract
回答的问题“这些 UB-affecting passes 执行后会得到哪些 allocation、lifetime、alias、offset 和 peak？”“经过这个 stage 后，先前哪条最小资源事实仍然必然成立？”
状态完整度较高的 GenericModule：operation、region、block、type、attribute、effect；之后还有 SemanticIR/PlanMemory 状态稀疏 MURG：只保留 hard reject 所需的 payload、instances、alias、lifetime、witness 和 trace
执行方式按真实顺序改写 GenericModule，bufferize，构造 gen/kill 与 inplace/multibuffer，最后执行 PlanMemory逐 stage Preserve / Transform / Invalidate；通常不生成 lowering 后 IR，也不规划 offset
输出精度支持范围内追求 Exact；不精确路径为 Incomplete只输出安全下界；信息不足即丢弃该条事实并 defer
代价与维护精度高，但接近维护一个轻量后端副本，成本较高运行轻、适合 autotune 前置过滤，但更保守、覆盖率较低
关键边界：现有模型的主入口是 before/after CVPipelining 的 Generic IR，而当前过滤器入口是 canonical TTIR。二者不是同一 IR 边界，不能把现有模型直接当作 TTIR contract 调用；否则必须先完成 TTIR→HIVM/Generic IR lowering，可能失去“提前过滤”的收益。

验证 contracts 与真实编译快照
  1. 先定义两个模型的 IR boundary 和字段映射；不要按 pass 名字机械地重复写一份公式。
  2. 对简单 stage，从现有 pass 语义提炼 Preserve、公式或关系摘要，并把严格前置条件写进 contract。
  3. 对 CVPipelining、SplitMix、bufferization、multibuffer 等复杂 stage，优先抽取/共享现有语义 helper；若无法在 TTIR 入口安全摘要，就 Invalidate/defer。
  4. 现有重放模型和真实编译 snapshot 用作 contract 的认证 oracle；样本通过是必要测试证据，但不能代替代码级前置条件和 fail-closed 逻辑。
实现结论：ResourceContract = 已有 pass 语义的保守摘要。有时表现为公式，有时是 alias/lifetime 等结构规则；只有边界匹配时才调用语义重放。它不是“operation → UB 使用率查表”，也不是第二套完整模拟器。

10. Contract 如何作用于资源，以及如何求下界

单资源示例

Matchertensor<131072xfp16>
R0 ≥ 256 KiB
→
MaterializationContract证明 GM→UB allocation
R0 ≥ 256 KiB
→
TileContract最多 4 tiles
R0 ≥ ceil(256/4)=64 KiB
→
BufferizationContractPreserve
R0 ≥ 64 KiB

如果中间任一 stage 可能进一步缩小/消除资源却没有 transfer function，则 R0 失效，结果 defer。

多资源求解

Singleton certificate

LBsingle = max(bytes(r) × minInstances(r))

当前生产分析只启用这一类；certificate 同时复制获胜资源的完整 contract_trace。

Coexistence certificate

LBwitness = Σ bytes(r) × minInstances(r)

只有同一 witness 中所有资源有效、两两 mustDistinct，且不存在 mayAlias 才能求和；certificate 合并 witness 与各资源的 contract trace。

没有“fit”结论：LB ≤ capacity 只能说明当前证明不足以拒绝，真实 peak 仍可能更高，因此必须 defer。

12. 建议落地计划

P0 · 打通可执行合同链 Implemented

已把真实 pass builder 同步记录为 ordered stage contexts，实现严格 packaged schema、profile → registry 装载、contract id/version 绑定和 identity/stage golden；BiSheng 未公开的内部 pipeline 作为由 compiler 内容哈希约束的原子 suffix stage。

已覆盖：人工 profile 可运行 fail-closed contract；pass/order/option/version/identity 任一漂移稳定 defer。canonical TTIR → before CVPipelining 的语义字段映射随 P1 首个 materialization contract 落地；最终 certificate 与 debug JSON 已保留完整 contract_trace，可回溯每条下界事实经过的 matcher/contract。

P1 · Direct-copy 生产闭环 In progress

已实现参数化 direct-copy-preserve@1、direct-copy-max-tiles@1、canonical TTIR hash 绑定，以及不安装 profile 的 oracle candidate chain。候选链通过 candidate-only API 执行；生产 API 只接受带完整 promotion 认证元数据的 active profile。max-tiles 使用 ceil(payload/maxTiles)，绑定真实 ttir.triton-to-linalg stage，并与 before-CVPipelining snapshot 中唯一静态 local allocation 交叉验证；promotion 还要求 certificate 的 contract_trace 精确等于 source matcher + ordered candidate contracts，不能用其他合同链生成的证书冒充。后续 BiSheng suffix 只能 Preserve 或 Invalidate。首版仅允许 compile_mode=simd、multibuffer=false，资源事实或 stage 漂移即 Invalidate。

当前门禁：oracle 通过 suffix compiler 的 post-TileAndBindSubBlock 真实 stage snapshot 检测 get_sub_block_idx，得到实际 auto-tile outcome；同时调用 cvpipeline_ub_model_cpp 对 before-CVPipelining IR 做 exact semantic replay。snapshot 缺失、重放非 exact、二者 status/scope/peak/capacity 不一致或与 fixture 不一致均 fail closed。fixture 还显式记录 tile_mix_cube_loop / tile_mix_vector_loop，同一参数同时传给真实 suffix 和语义模型，禁止依赖默认值。当前纯 AIV direct-copy fixture 已在目标 CANN 环境完成完整联合验证：contract LB 为 4096 bytes，21 次 semantic replay 与真实 PlanMemory peak 均为 32768 bits，outcome 均为 false，violations/unavailable 均为 0；candidate 只供人工审核，生产 profile 继续保持空。

验收：direct-copy fixtures 同时经过真实 compiler snapshot、现有语义重放和 contracts；seed 0..19 上满足 LB ≤ min actual peak，且 reject 的 config 全部真实 overflow。

P2 · Elementwise 与 alias/coexistence In progress

第一条最小切片已实现：严格匹配 load(lhs) + load(rhs) → arith.addf → store，生成两条 GM→UB resource、pairwise mayAlias 和同一 program point 的 CoexistenceWitness；materialization 前的 binary-add-preserve@1 只保持 mayAlias，binary-add-max-tiles@1 在物化阶段验证完整 source facts 后才精化为 mustDistinct，后续 preserve 保持该强关系。solver 只有看到 mustDistinct 才允许把两条资源相加。

第二条最小切片也已实现：严格匹配无 allow_reorder / efficient_layout 的 load → reshape → [inverse reshape] → store。真实认证 fixture 使用 value tensor 的 rank-1→rank-2→rank-1 严格逆变换，使 pointer 始终留在已验证的连续一维 lowering 路径。matcher 为 load 和 view 建立两个逻辑 resource node，但只先记录 mayAlias；reshape-copy-max-tiles@1 必须在 materialization stage 证明二者落到同一个 allocation，才精化为 mustAlias。solver 按 alias class 取一次大小，因此不会把逻辑 view 重复计入 UB。

当前门禁与结果：solver 仅对同一 witness 且 pairwise mustDistinct 的资源求和；mayAlias、重复 resource id、缺少 witness、合同顺序或参数漂移均不能产生双资源证书。多资源 certificate 原样保留重复 contract ID，能够表示每一个真实 stage。binary-add 的两个边界 allocation 均为 262144 bytes，analyzer LB 为 524288 bytes，真实 PlanMemory 与语义模型均得到 required/peak 4194304 bits、capacity 1572864 bits 的 UB overflow。reshape-copy 的真实边界只有一个 262144-byte allocation，analyzer singleton LB 为 262144 bytes，真实 PlanMemory 与语义模型均得到 required/peak 2097152 bits、capacity 1572864 bits 的 UB overflow。两类均在目标 CANN 环境完成 20 seeds + retry，auto-tile outcome 全为 false，violations/unavailable 均为 0；candidate 已生成但未安装。broadcast、expand_dims、bitcast 继续具名 defer。

fixture 准备：新增 ttir_ub_fixture_bundle.py，要求同一次编译捕获的 kernel.ttir.mlir 与紧邻 createCVPipeliningPass 之前的 before_cvpipelining.mlir 位于同一专用目录。工具会核对 family-specific allocation 数量和 ceil(payload/max_tiles) 精确大小，raw kernel.ttadapter.mlir 会被拒绝；随后写出严格 manifest 和两个文件哈希，并拒绝缺失、跨目录路径及覆盖已有 fixture。新 fixture 的 auto-tile outcome 与 expected analyzer decision 均默认为 null，不再要求人工猜测；oracle 从真实运行推导 outcome，并要求每个 analyzer reject 都由真实 UB overflow 证明。schema 同时独立验证 payload = source_elements × element_bit_width / 8，因此绕过打包器手写不一致 proposal 也会 fail closed。

下一步：人工审核 direct-copy、binary-add、reshape-copy 三类 candidate，不自动写入 packaged profile；同时保存 broadcast/expand_dims/bitcast 的真实 lowering snapshot，再按证据决定扩展合同或继续 defer。验收：禁止把 mayAlias 或不同 witness 的资源相加，也禁止把 mustAlias view 重复计数；真实可编译误拒绝数为 0。

P3 · Reduction、loop 与 multibuffer In progress

第一条 reduction 最小切片已实现：严格匹配唯一的一维连续 f32 load → tt.reduce(axis=0, arith.addf) → scalar store，只接受偶数元素、无 mask/特殊 cache/fast-math、单一 reducer region 和单一结果 use。matcher 建立三条逻辑资源：输入 payload、ReductionScratch = input/2、4-byte ReductionAccumulator，并记录三资源 CoexistenceWitness；任何 shape、combiner、dataflow 或 store 语义漂移均具名 defer。

合同链不是把 scratch 当成 TTIR 已有 allocation：reduction-sum-preserve@1 只传递资源事实；当前 reduction-sum-max-tiles@1 只接受经真实 lowering 认证的 max_tiles=1；直到原子 BiSheng suffix 的 reduction-sum-extra-buffer@1 验证 AllocExtraBuffer 行为后，才把 input/scratch/accumulator 从 pairwise mayAlias 精化为 pairwise mustDistinct，solver 才能给出三者之和的 witness certificate。多 tile reduction 没有套用未经证明的公式，继续 defer。

真实证据：before-CVPipelining snapshot 只有一个 262144-byte source allocation；现有语义模型的 debug 账本显示 reduction scratch 为 131072 bytes、accumulator 为 4 bytes，三者在 reduction 点同时存活，实际未对齐峰值为 393220 bytes。analyzer 因此给出同值下界和 resource_ids=[0,1,2] 证书；真实 PlanMemory 与 semantic replay 在 20 seeds + retry 上均得到对齐后的 3145984 bits UB overflow（capacity 1572864 bits），auto-tile outcome 全为 false，6-case 联合报告 violations/unavailable 均为 0。candidate 已生成但未安装。

第二条 loop-carried liveness 最小切片已实现：严格匹配固定 0..2 step 1 的单 scf.for，数据流必须是 init load → iter_arg accumulator，loop body 只能包含 step load → arith.addf(acc, step) → scf.yield，loop 结果单独写回。matcher 建立 loop-carried-accumulator 与 loop-step-input 两条资源：前者从 loop 前的 load 活到 loop 后 store，后者在 loop program point 产生并消费，并建立二资源 CoexistenceWitness。trip count、body、fast-math、pointer、load/store 或 use 数量任一漂移均 defer。

loop-carried-add-preserve@1 只能保持已知 liveness；loop-carried-add-max-tiles@1 仅接受真实认证的 max_tiles=1，并在物化阶段确认两个独立 allocation 后把 mayAlias 精化为 mustDistinct。真实 before-CVPipelining snapshot 显示 loop 外 accumulator allocation 和 loop 内 step allocation 各 262144 bytes；analyzer 下界为 524288 bytes。真实 PlanMemory 与 semantic replay 在 20 seeds + retry 上均得到 4194304 bits UB overflow（capacity 1572864 bits），auto-tile outcome 全为 false，violations/unavailable 均为 0；candidate 已生成但未安装。

第三条固定 multibuffer 子切片已实现：真实 MarkMultiBuffer 只对 loop 内 GM→UB step load 标记 factor=2，PlanMemory 随后把该 storage entry 展开为两份物理实例。loop-carried-add-multibuffer@1 仅在前序合同已经证明两个资源 mustDistinct、suffix stage 与 options 精确匹配且实例参数恰为 2 时，调用单调的 raiseResourceInstances(step, 2)；accumulator 仍为一份。因此 analyzer 下界为 262144 + 2 × 262144 = 786432 bytes。真实 PlanMemory 与 semantic replay 在 20 seeds + retry 上均得到 6291456 bits UB overflow（capacity 1572864 bits），6-case 联合报告 violations/unavailable 均为 0；candidate 已生成但未安装。

剩余工作：为 num_stages、更多 loop depth/trip count、buffer count、preload factor=4，以及 Dynamic CV inner/outer multibuffer 的边界组合补同编译 snapshot、semantic replay 与真实 PlanMemory fixtures。验收：当前证据不得外推到 factor≠2、不同 bounds、嵌套 loop、scan、argmin/argmax、多 tile、preload 或 Dynamic CV multibuffer。

P4 · Dynamic CV / MIX / irregular memory

对 DynamicCVPipeline、SplitMix、AIV/AIC 投影和 multibuffer，优先抽取并共享 cvpipeline_ub_model_cpp 的 pass semantics、alias/liveness helpers；不能形成小型安全摘要的路径保留 replay-backed shadow 或直接 defer。再扩展 descriptor、gather/scatter/index/unstructured memory。

验收：共享语义只有一个事实来源；core projection、跨 core copy、inner/outer multibuffer 的 contract trace 均能回链到 replay/snapshot fixture。

P5 · Dot、alignment 与长尾

明确 Cube 资源非目标边界；只在 UB/AIV 部分有完备合同后支持 dot；补 alignment、atomic、custom ops。

验收：各 operation family 均有 coverage matrix：supported / deliberate-defer / unsupported-reason。

Rollout · off → shadow → enforce

默认 off；CI/代表性 workload 开 shadow；任何下界违规立即撤销对应 profile；零违规门禁后才允许显式 enforce。

13. 风险、验证与决策门禁

主要风险

  • 把 logical tensor size 错当 physical buffer size。
  • 遗漏外部 BiSheng/CANN 内部 tiling 或 elimination。
  • 把两个不同 SSA value 错当 mustDistinct。
  • 两两 overlap 被错误提升为多资源共同 coexist。
  • 版本或 option 漂移后继续复用旧 contracts。
  • oracle 只覆盖样本，合同本身缺少代码级前置条件。

硬门禁

LB(config) ≤ min ActualUBPeak(config, seed) seed = 0..19
  • 模型下界违规数必须为 0。
  • 每个 analyzer reject 必须由真实 PlanMemory 证明 overflow。
  • 真实可编译 config 被拒绝数必须为 0。
  • profile 只能人工审核加入，不由 oracle 工具自动发布。
