## Oracle gate result: blocked, not passed

The same-schema suffix tool requires the exact BiShengIR source and its matching
complete LLVM/MLIR development build.  The compatibility patch correctly
disabled BiShengIR Python bindings, but the Triton cached LLVM package is a
runtime/release package.  Its CMake exports do not provide generated MLIR
targets required by BiShengIR, including:

```text
BiShengIRLinalgDialectExt
MLIRLinalgTransformEnumsIncGen
MLIRMemRefPassIncGen
MLIRTensorTransformsIncGen
```

Consequently configuration of `bishengir-cvpipeline-suffix-compile` fails before
the target can be built.  This is an environment artifact incompleteness, not a
passing oracle result.

The installed CANN tool cannot substitute for it.  Its SHA256 is:

```text
bishengir-compile
4a1312e7d3aa2d21a220b3acd081e90d7b4a3d043af5da98e8cfc681c13048ef
```

When given the rebuilt `libtriton` P4 boundary it rejects the input with:

```text
'hivm.hir.fixpipe' op operand count (2) does not match ... operandSegmentSizes
```

That is a producer/consumer schema mismatch, so using it would invalidate the
same-schema requirement.  No `cvpipeline_ub_model_cpp` executable/source and no
UB C++ GTest binary were present in the container work area; the latter was not
built because the release build uses `TRITON_BUILD_UT=OFF`.
