## Oracle gate result: blocked, not passed

The same-schema suffix tool requires the exact BiShengIR source and its matching
complete LLVM/MLIR development build.  The compatibility patch correctly
disabled BiShengIR Python bindings, but the Triton cached LLVM package is a
runtime/release package.  Its CMake exports do not provide generated MLIR
targets required by BiShengIR, including:

```text
BiShengIRLinalgDialectExt
MLIRLinalgTransformEnumsIncGen
MLIRMemRefPassIncGen
MLIRTensorTransformsIncGen
```

An isolated full LLVM+MLIR development build was subsequently completed from
the source bundled with AscendNPU-IR.  The decisive detail is that the vendor
patches are an **ordered series**, rather than patch 0051 alone: applying every
`build-tools/patches/llvm-project/*.patch` with the upstream `patch -p1 --merge`
workflow restores `ExpandShapeUtils`, the extra iterator values,
`LinalgExtensions`, and `BiShengIRLinalgDialectExt` together.  The resulting
same-source suffix compiler built successfully with SHA256
`0f1bb44d67cb9ed07c545d340bda7f4a391d6687d57158ca169a43759eeeb762`.

This resolves the LLVM build-API blocker but not the independently required
boundary-schema gate.  The current source definition of `hivm.hir.load` has no
`eviction_policy` or `core_type` assembly fields, while the rebuilt libtriton
P4 boundary contains both.  The new suffix compiler therefore stops while
parsing `eviction_policy = <EvictFirst>`.  Silently dropping or rewriting that
field would make the suffix pipeline different from the producer, so the oracle
must keep this as a fail-closed unavailable result.

The one-seed unified oracle was also exercised in the same container with this
binary.  Its report has nine cases, zero violations, and one unavailable:
`dynamic-cv-mix-dot-exp-f32-16x16` is unavailable because no
post-`TileAndBindSubBlock` snapshot can be emitted after the parser failure.
This is evidence for the schema gate, not a passing oracle result and not a
reason to promote any profile.

An older Ascend LLVM commit, `2f203398`, does contain both the extension target
and `LinalgExtensions.cpp`.  An isolated LLVM+MLIR+BiShengIR build completed
there and produced a suffix binary with SHA256
`5680aab6b6bf6890fa945aabeeaf4a6224dfa429d17e162f40b66700f6f2d3bd`.
It is **not** a valid substitute: the current P4 before-CVP boundary fails to
parse at `hivm.hir.load ... eviction_policy = <EvictFirst>` because that older
consumer does not recognize the current producer syntax.  The all-seed suffix
run consequently has zero violations but 21 unavailable Dynamic runs (seeds
`0..19` plus retry), all due to the missing post-TileAndBindSubBlock snapshot
after this parse failure.  This confirms the toolchain must match both the
extension build API and the boundary schema.

The installed CANN tool cannot substitute for it.  Its SHA256 is:

